SECTION 01

Overview & product principles

ARIP is not a chatbot. It is a decision system with a UI. Every screen in this specification exists to make an AI decision visible, correctable, and defensible. The design language is deliberately dense and utilitarian — closer to a trading desk or an incident console than a marketing site — because the primary user is a support agent who lives in the queue for eight hours a day.

1

Explainability is chrome, not a feature

Confidence, citations, and the rule that fired are visible at every altitude: badge in the list, panel on the record, full trace in the drawer, immutable entry in the audit log.

2

Rules outrank the model

Where a business rule overrides an AI decision the UI says so explicitly, in the same visual weight as the decision itself. A 98% confident answer held for Legal review is a success state, not a failure.

3

Keyboard-first density

32px table rows, a three-pane queue, J/K navigation, and a command palette. Nothing important requires the mouse.

4

Configuration over customization

Thresholds, routing, prompts, and workflows are all data. Every admin surface is a CRUD screen over a versioned, approvable, rollback-able configuration object.

Confidence matrix — the single most important business rule in the product
Confidence Decision UI treatment Human in the loop
95–100% Auto reply Green badge, sent state, citations attached Post-hoc sampling only
80–94% Draft reply + optional review Blue badge, editable draft, Approve / Edit / Reject Agent one-click approval
60–79% Ask clarification Amber badge, generated question set, awaiting-customer state Agent may skip and answer directly
< 60% Escalate / route Red badge, routing suggestion + knowledge-gap prompt Mandatory human ownership
Override: categories flagged Legal, Compliance, or Complaint · regulated never auto-reply regardless of confidence. The decision engine emits rule_override and the UI shows a held-for-review banner. (BRD §15, PRD FR-030.)

Navigation model

  • Persistent left sidebar, 248px, collapsible to a 56px icon rail (state persisted per user).
  • Groups are labelled, not collapsible — collapsing hides work from agents.
  • Second-level navigation is horizontal tabs inside the module, never a nested tree.
  • Records open in-place with a URL, never in a modal — deep links must survive a paste into Slack.
  • The decision trace is a right-hand drawer (560px) so the record stays in context behind it.
  • Command palette on ⌘K jumps to any request, article, rule, or module.

Object model exposed in the UI

  • Request — the spine. Everything else hangs off it.
  • Decision — one per AI evaluation; a request may have several over its life.
  • Evidence — citation linking a decision to a knowledge chunk or node.
  • Workflow run — the actions taken after a decision.
  • Knowledge article — versioned, lifecycle-governed, department-owned.
  • Audit event — append-only; every screen above writes here.
SECTION 03

Personas & user journeys

Context: Nordbank, a mid-size European retail and business bank. Eight roles, one platform. The Support Agent is the design centre of gravity — every other role's screens are judged by whether they make the agent's day easier or the bank's regulator calmer.

PR
Priya Raman
Support Agent · primary persona
Hero

Handles 60–90 requests a shift across retail banking. Lives in the queue with two monitors. Trusts the AI only as far as she can see its sources.

Goals
  • Clear the approval queue before SLA breach
  • Never send an answer she cannot defend
  • Escalate the right things, not everything
Pains
  • Opaque AI suggestions she has to re-verify from scratch
  • Context switching between mail, policy PDFs and the ticket tool
  • Being blamed for a machine's wrong answer
Design response: three-pane queue with keyboard nav, citation chips inline in the draft, one-click Approve, and a decision trace that shows exactly which clause was used.
MC
Mei Lin Chow
Knowledge Manager

Owns the corpus the AI is allowed to speak from. Answers to compliance when a policy is quoted wrongly.

Goals
  • Keep approved knowledge current and provably in-date
  • Close gaps the AI keeps failing on
  • Prove which article answered which request
Design response: lifecycle-first library, expiry warnings surfaced before they bite, gap backlog ranked by hit count, AI-assisted drafting seeded from failed requests.
DO
Daniel Okafor
Department Manager — Cards & Payments

Accountable for his queue's SLA and for anything routed to him wrongly.

Goals
  • See breach risk before it happens
  • Rebalance load across agents
  • Send mis-routed work back with a reason that trains the system
Design response: SLA-sorted department dashboard, reassignment with mandatory reason code that feeds routing accuracy metrics.
TB
Tomas Berg
Administrator

Tunes the machine. Changes a threshold on Monday and must explain the automation-rate swing on Friday.

Goals
  • Change behaviour without a deployment
  • Simulate a rule change before it ships
  • Roll back a bad prompt in seconds
Design response: every configuration object is versioned with diff, dry-run simulator against last 30 days of traffic, one-click rollback, change requires approver above a blast-radius threshold.
AV
Alice Vandermeer
Executive — COO

Approved the budget on a 70% manual-effort reduction. Checks it on a phone, twice a week.

Design response: a five-tile KPI board against BO-001…BO-005 targets, trend not snapshot, mobile-first layout, scheduled PDF to the board pack.
KI
Ken Ishida
Compliance Auditor · Super Admin & Customer also modelled

Must reconstruct, months later, why a customer got the answer they got — including the exact prompt and policy version in force at the time.

Design response: read-only everywhere, immutable audit stream with a trace-by-request lookup, point-in-time knowledge and prompt versions pinned to each decision, signed export.

SECTION 04

Design system

A restrained, high-density enterprise system. One neutral ramp, one brand blue, one AI violet, three semantic colours. Colour carries meaning only — decoration is done with space and rule weight. Every token below is given as a CSS custom property name so it can be pasted straight into the implementation.

Accessibility — WCAG 2.2 AA commitments

Perceivable
  • Body text ≥ 4.5:1, large text and UI borders ≥ 3:1 — all tokens above verified
  • Status never colour-only: shape + label + value
  • Charts carry a data-table equivalent behind a toggle
  • Supports 200% zoom and 320px reflow without horizontal scroll
Operable
  • Full keyboard path through the queue: J/K rows, Enter open, A approve, E escalate, Esc close
  • Focus trapped in drawer and modal, restored on close
  • Skip-to-content link; no keyboard traps in the workflow canvas (arrow-key node mode)
  • No time-limited actions except SLA countdowns, which are informational
Understandable & robust
  • Errors identified in text, adjacent to the field, with a fix suggestion
  • Destructive and irreversible actions require typed confirmation
  • aria-live="polite" on pipeline progress and toast region; assertive on SLA breach
  • Semantic tables with scope, sortable headers announce sort state
  • prefers-reduced-motion disables the pipeline animation, keeps state text

ARIP is a desk product first — agents work on 1440px+ screens. Tablet and mobile are for approval, triage and executive oversight away from the desk, so they drop configuration surfaces rather than shrinking them. Nothing critical is desktop-only: every approval, escalation and routing action is reachable on a phone.
